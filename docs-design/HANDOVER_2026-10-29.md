## 2. How the owner wants the work done

These come from `AGENTS.md`, `docs/TESTING.md` and the owner's standing instructions. Break them and the owner will notice.

- **Strict test-first.** A failing test is written and run, and seen to fail for the right reason, before the production code for it exists. A test that cannot compile is not a red test: add a stub that compiles and does nothing, and see the assertion fail. Do not ask whether to write tests first.
- **Do not commit.** The owner commits and pushes their own work. Never add assistant or AI attribution to commits, pull requests, code or documentation.
- **Verify on Jenkins when it is reachable, otherwise run every suite locally against Docker Desktop** (section 5), without stopping to ask. Never remove Docker volumes without listing them and getting the owner's word.
- **Run builds in a visible console**, through `Tee-Object` into `logs/`, never hidden in the background.
- **Logs are part of the result.** A run is accepted only after the retained Maven output, application logs, helper-subprocess logs and Docker archives have been read. Any ERROR, or any stack trace at any level, that is not flagged `*** INTENTIONAL ERROR: ... ***` or `*** INJECTED FAILURE: ... ***` is a defect to find and fix. Never filter it, lower its level, or change a log's level or frequency unless asked. See `docs/TESTING.md`, "Intentional error flags and log auditing".
- **Declare an intentional error only with evidence.** Establish what the test did that caused it, give it the narrowest definition that matches (a definition can also name the exception the event carries), say why in a comment beside the declaration, and declare it only in the class where it was seen.
- **A race or an intermittent failure is a defect.** Find the cause and check production for the same race. Do not retry it away; the owner had the image-build retry removed for this reason.
- **Compare with industry practice.** The owner asks that designs be checked against HashiCorp Consul (and its `hashicorp/raft`); quote the source when you do.
- **Clean code, no loose ends.** Resolve inconsistencies in code and documents when found. When a change removes a state transition, first list every observable effect the old transition had, mark each removed or kept on purpose, and write a failing test for each effect that must survive (Pre-Vote lost a cleared-leader effect this way; see design section 14.10).
- **Task lists and handovers** live in `docs-design/` with the date of their last change in the file name. Rename one on the day it changes, update every reference (a list renamed for a link counts as changed, so lists that link each other are renamed together), and archive a finished list to `docs/archive/` without asking.
- **Words:** Qraft has only "server mode" and "client mode". Do not use the two retired words for the components.
- **Files:** every new Java file has the Apache header and an `@author`, `@since` and `@version` Javadoc. The working tree is CRLF; normalise files written by tools (on Windows, `sed -i` writes LF: check with `file`, fix with `unix2dos`). No Mockito. Time and sleeping go through injected clocks and timer helpers in tests. PIT is shelved.

## 3. What changed since 2026-10-26

All of it is committed and pushed, and the last full run passed on it (below).

- **Client list Phase 1 closed** (`7a1ed98`): the server's service and check writes moved to `/v1/catalog/register`, `/v1/catalog/deregister` and `/v1/catalog/check/observe`.
- **The Docker image-build retry was removed.** A daemon that loses a snapshot is a fault to investigate, not to retry.
- **Client list Phase 2, client side** (`6680a67`): a required `client.dataDirectory`, locked to one client (`client.lock`); a generated node ID kept in `node-id` through `common.storage.IdentityFile`, which `ServerIdentity` now shares; `client.id` became `client.nodeName`, defaulting to the host name.
- **The start scripts rebuild their images** (`14ded7d`): every `docker compose ... up -d` passes `--build`, because the scripts had started stale images.
- **A wedged snapshot transfer** (`f991254`): an InstallSnapshot answer from another server ID was ignored but its transfer never ended, and removing a server did not forget its transfer or backoff, so a replacement under the old name got nothing for the rest of the term. Both fixed, test first.
- **Deadlines on every Raft call** (`06a5210`, `ee11971`): 10 s for a vote, pre-vote or append, which is Consul's Raft transport timeout. A snapshot chunk gets Consul's rule, 10 s for every whole 256 KiB and never less, so 40 s for a full 1 MiB chunk. Before this a call on a connection that died without a reset never failed and logged nothing, and a stuck chunk wedged the snapshot transfer the same way as above.
- **Keepalive on every Raft connection** (`ee11971`): gRPC ends only the call at a deadline and keeps the dead connection, where Consul closes it. The transport now pings after 10 s without a read (gRPC's minimum) and closes the connection if the ping is not answered in 10 s; `GrpcRaftServer` permits pings every 5 s, with or without a call, or gRPC would close the connections with `too_many_pings`. `GrpcRaftKeepaliveTest` (tagged `slow`) covers both.
- **Audit definitions can name an exception** (`06a5210`): `GRPC_ANSWER_TO_KILLED_PEER` accepts Netty's `Stream Error` warning only with `Stream closed before write could take place`. New or newly declared errors, each traced to its cause: `RAFT_SNAPSHOT_CHUNK_UNANSWERED` (`bc19492`; the partition test cuts a follower's network, so the leader's snapshot waits until its deadline), `RAFT_SNAPSHOT_TRANSFER_INTERRUPTED` in `DockerLostQuorumRecoveryTest` (its offline backup stops a server), `RAFT_PEER_NAME_UNRESOLVED` in `DockerStartCommandsTest` (Docker Desktop starts the scripts' containers one at a time). `DockerStartCommandsTest`'s cleanup has a 5-minute budget instead of JUnit's 15 s default.

**Last full run, on the code of `bc19492`:** default 1,233 with every coverage gate met, end-to-end 10, Docker and `slow` 43 (28 min 24 s), no failures, errors or skips. 232 retained logs: 833 ERROR lines, all flagged; 566 stack traces, none unflagged; no `too_many_pings`; no JVM crash file. Details in `docs/JENKINS.md`, "Local run in place of Jenkins".

## 4. What comes next

1. **Phase 2's design was checked against Consul on 2026-10-29** (`agent/consul/state/catalog.go`, `ensureNodeTxn` and `ensureNoNodeWithSimilarNameTxn`, and the agent's anti-entropy in `agent/local/state.go`), and the owner decided four points, now in decision 8: a rename follows Consul; a registration with an ID claims the name of a node without one; names conflict regardless of case; a `REGISTERING` node holds its name.
2. **Phase 2, server side** (decision 8 in the client list):
   - store the node ID with the node in a new optional protobuf field, so older entries and snapshots still load;
   - refuse a name that a `REGISTERING` or `HEALTHY` node of another ID holds with `409 node_name_reserved`, comparing names regardless of case;
   - allow a takeover once the holder is unreachable or reaped, removing the old node's services and checks in the same replicated step, and refuse the old ID if it returns while the new holder holds the name;
   - let a registration with an ID claim the name of a node without one, keeping its services and checks;
   - rename a node whose ID returns under a new name as Consul does: remove it under the old name with its services and checks and insert it under the new one, in one step; the client's reconciler registers its services again. Refuse a rename to a name another node holds, or a node without an ID holds.
3. Fixtures for entries and snapshots written without a node ID, and replica-determinism tests for the takeover and rename commands.
4. Record the decision in the design: section 7.3, which says a host name alone is not a sufficient identity, and section 22, which lists client identity as open.

**Exit:** red before green, with tests of the conflict, takeover and rename guards, including a takeover that must not leave the old node's services in place, a rename that must not leave them under the old name, and a claim of a node without an ID that must keep them; a wiped-directory restart scenario passes end to end. The list's rules apply: `mvn install` at the end of each phase, and the full suites for any phase that changes the runtime.

## 5. Running things

- **JDK 27 and Maven 3.9.16.** On the `markr` workstation `JAVA_HOME` is `C:\Users\markr\.jdks\openjdk-27`; on the earlier machine it was `C:\Users\mraysmit\.jdks\openjdk-27-1`. A shell that defaults to another JDK gives wrong results.
- **The three suites**, as the Jenkinsfile runs them, one after another:
  1. `mvn -B --fail-at-end clean install` (default suite and coverage gates, about 3 minutes);
  2. `mvn -B test -Dgroups=e2e -Dtest.excludedGroups=` (about 1 minute);
  3. `mvn -B test -Dgroups=docker,slow -Dtest.excludedGroups=` (26 to 31 minutes on Docker Desktop). On Windows use the comma: `mvn.cmd` runs through `cmd.exe`, which reads the Jenkinsfile's `docker|slow` as a pipe.

  In PowerShell, quote every `-D` argument, or `-Dtest.excludedGroups=` is split in two. A test named with `-Dtest=` is still excluded by its tag unless `-Dtest.excludedGroups=` is also given.
- **Where the Docker stage's time goes:** the classes run one at a time; five of them wait on the cluster's own timers (a follower stopped for 200 s, the 60 s cleanup grace), about 12 minutes; the start-script tests take about 5; 23 cluster starts and removals take about 3. The breakdown and the options to shorten it are in `docs/JENKINS.md`.
- **Docker tests** need `mvn package` first: a freshness guard checks that `target/qraft.jar` is current. They build their image once per run, with `docker compose build`, and a failed build is never retried.
- **The IDE** can leave stale class files that throw "Unresolved compilation problem". Delete the class files under `target/test-classes` and rebuild.
- **Jenkins** (`http://192.168.137.32:8080/job/Qraft/`) builds the pushed `main`; `.\.env\qraft-jenkins-build.ps1` starts a build, follows it, and saves the console and archived logs under `logs/jenkins/Qraft-<n>/`. From the `markr` workstation it does not answer, and the local `jenkins/jenkins:lts-jdk21` container has no Qraft job, so every run since 2026-10-27 has been local. When Jenkins is used, a start request that times out may still have queued a build: ask for the last build (`job/Qraft/api/json?tree=lastBuild[number,building]`) before starting again. A build that fails before any test ran is an infrastructure failure and says nothing about the code.
- **Auditing a run.** Count the ERROR lines in the Maven output and in every log the run wrote under `logs/` (the Docker archives are under `logs/docker/<class>/`), require that every one carries a flag, and check that no stack trace is unflagged; a flag on an exception header covers its trace. Also look for JVM crash files (`hs_err_pid*`, `*.dumpstream`). One known false positive for a simple checker: the `lock-contender` trace in `DockerDurableRestartTest` is flagged on its "Exception in thread" line.

## 6. Known open items

- **An unexplained leader step-down.** In the run that wedged the snapshot transfer, the leader counted no answer from `server1` for 1.5 s while `server1` went on receiving its heartbeats, and stepped down by check-quorum. The best lead: `hashicorp/raft` handles heartbeats on a fast path "to avoid head-of-line blocking"; Qraft's heartbeats share the path of ordinary appends, so an answer can queue behind slower work on the follower. Not yet investigated.
- **The Docker stage's length.** Options the owner has not decided: a shorter cleanup grace configured for the tests (about 3 to 4 minutes saved), a lower gRPC reconnect-backoff cap so `DockerReturningVoterTest` can stop its follower for less than 200 s, `DockerStartCommandsTest` in a stage of its own (about 5 minutes), or classes in parallel on separate clusters.
- **The start scripts' name-lookup warnings** are declared as expected in `DockerStartCommandsTest`. They come from the scripts starting every server at once, which users see too; making the scripts wait for each server is the alternative, and the owner's to choose.
